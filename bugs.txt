[NEW2-CRIT-B] amazon_checker: session closed before fallback uses it
File: core/amazon_checker.py:191,219,222
amazon_check_batch() calls _sequential_fallback() while the
finally block (line 225) closes the session AFTER the fallback
returns. BUT _sequential_fallback() calls amazon_check_single()
which creates its own session (owns_session=True), so it never
reuses the batch session — however the batch session is passed
to _sequential_fallback (parameter session=session), which then
passes it on to amazon_check_single. amazon_check_single checks
owns_session = (session is None). Because session is NOT None,
it re-uses the batch session without closing it — and then the
outer finally closes it again on next iteration. This means the
second sequential call gets a closed session, causing
"Session is closed" aiohttp errors on batch fallback.

[NEW2-MED-B] ccgen: /ccgen <count> only accepts digit-only args
File: handlers/ccgen.py:60
args[0].isdigit() fails for "10" when user types /ccgen 10 —
this actually works, BUT if user types /ccgen 50 it also hits
the elif len(args)==2 branch (args=[50]) which tries normalize_bin("50").
normalize_bin("50") succeeds (2 digits, 1-10 range) returning
"50" as the BIN prefix — so /ccgen 50 is misrouted into the
"bin + count" branch (len==2), using "50" as a BIN prefix
instead of a count. Users get cards with BIN "50..." not 50
random cards, unless they write exactly /ccgen <N> where len(args)==1.
Actually re-reading: len(args)==1 is checked first (line 58).
The real bug is: /ccgen 50 → args=["50"], len==1, isdigit→True,
range check: 1<=50<=50 → count=50. Works. But /ccgen 479851 10
→ args=["479851","10"] len==2, normalize_bin("479851")→"479851",
args[1]="10" isdigit and in range → count=10. Also works.
ACTUAL BUG: no 3-arg form (bin month year without count) —
the docstring says /ccgen <bin> <month> <year> <count> needs 4
args. A user typing /ccgen 479851 12 2028 sends 3 args
(len==3), which falls into the final elif (len>0 and not in
{1,2,4}) → usage error shown. Documented as 4-arg form but
common 3-arg variant (no count) gives an error with no hint.

[NEW2-MED-C] card_parser.py: colon-separator conflicts with time strings
File: core/card_parser.py:46-47
parse_card() tries ":" separator before " ". A card pasted
from some formats like "4798510629051356:12:2028:893" works
fine, but "4798510629051356 12 2028 893" is also valid. The
real bug: the separator loop tries each in order, and for ":"
splits on every ":" in the raw string. If the raw input
contains a URL or timestamp (user error), it will silently
try to parse garbage parts. No stripping of non-card content.
More critically: if the card is "4111111111111111:05:2026:123"
and the user accidentally adds spaces (e.g. from a copy),
parts split by ":" include internal spaces — parts[2] = "2026"
with leading space, which .strip() handles. Low severity but
can cause confusing parse failures.

[NEW2-MIN-B] cc_generator.py: Luhn doubling direction is inverted
File: core/cc_generator.py:68
_luhn_check_digit() doubles at even indices (i%2==0) of
reversed partial. In standard Luhn, the rightmost digit of
the *full* number is the check digit (position 0); the digit
to its left (position 1) is the first one doubled.
For the partial number (without check digit), position 0
of the reverse is what will become position 1 of the full
number after appending the check digit — so it should be
doubled. The code doubles at i%2==0 (positions 0,2,4...)
which is the opposite of the standard. The safety check at
line 102 (luhn_valid(number)) would catch any failure, but
if the algorithm produces wrong check digits silently caught
by the raise, those RuntimeErrors will propagate to users.
In practice, review luhn_valid doubling: it doubles at
i%2==1 (odd positions of reversed full number). The
_luhn_check_digit treats the partial reversed as if position
0 is already position 1 of final number — actually this
convention IS correct for computing the check digit.
Marking as low-priority: the safety assert at line 102
catches any invalid output, so functional correctness is
guaranteed; just the i%2==0 vs i%2==1 logic is confusing.
