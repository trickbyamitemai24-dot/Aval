HIGH (6) — Data corruption, hangs, or serious misbehavior
================================================================================

Bug #6 — Rate limiter mass-check counter leaks on error/abandon paths
  File: handlers/mass_check.py:84-161
  Issue: rate_limiter.can_start_mass(user.id) at line 84 increments the
         active-mass counter. But if the flow exits early (file too large,
         no valid cards, hourly limit hit), ConversationHandler.END is returned
         without calling rate_limiter.cancel_mass(). Also leaked if user sees
         buttons but never clicks any.
  Impact: After one abandoned session, the user is permanently locked out of
          mass checks ("You already have an active mass check"). Only a bot
          restart resets the counter.

Bug #7 — AdaptiveSemaphore replaces semaphore mid-flight, orphaning tasks
  File: core/mass_checker.py:86-88
  Code: self._semaphore = asyncio.Semaphore(self._current)
  Issue: When adaptive logic triggers a resize, it creates a brand-new
         Semaphore and discards the old one. Tasks that acquired the old
         semaphore release on the new one.
  Impact: After a resize, the concurrency limit is briefly violated. If scaled
          down, the new semaphore starts full, allowing a burst of tasks.

Bug #8 — browser_headers / api_headers mutate shared global profile objects
  File: core/anti_detect.py:73-81
  Code: prof = random_profile() then if ua: prof.ua = ua
  Issue: random_profile() returns random.choice(PROFILES) — a direct reference
         to the global list element, not a copy. Setting prof.ua permanently
         mutates that profile in the global PROFILES list.
  Impact: Every call with a custom ua permanently corrupts one random profile.
          Over time, the profile pool degrades.

Bug #9 — Charged/live card list messages can exceed Telegram 4096-char limit
  File: handlers/mass_check.py:439-449 (also lines 611-622 in resume_cmd)
  Issue: format_charged_cards_list and format_live_cards_list build a single
         message containing ALL cards. Each card entry is ~80-120 chars. With
         ~40+ cards, the message exceeds Telegram's 4096-character limit.
  Impact: telegram.error.BadRequest: Message is too long — the card list is
          silently lost. User never sees their results.

Bug #10 — 50,000 asyncio tasks created simultaneously for ULTRA tier
  File: core/mass_checker.py:479
  Code: tasks = [asyncio.create_task(check_one(c)) for c in cards]
  Issue: For ULTRA tier, cards can contain up to 50,000 entries. All 50K tasks
         are scheduled in the event loop instantly. While AdaptiveSemaphore
         limits active concurrency, all tasks consume memory (~1KB+ each).
  Impact: Memory spike of ~50-100MB. Event loop becomes sluggish. On low-memory
          systems (Railway free tier), this can cause OOM kills.

Bug #11 — resume_cmd lacks try/finally for rate_limiter cleanup
  File: handlers/mass_check.py:596-634
  Issue: mass_check_callback wraps mass_check() in try/finally with
         rate_limiter.end_mass() and complete_state() in the finally block.
         But resume_cmd calls mass_check() without any try/finally.
  Impact: If mass_check() raises during resume, rate limiter counter is never
          decremented. User is permanently locked out of mass checks.

Bug #12 — increment_check_stats crashes on unrecognized status
  File: core/database.py:186-197
  Issue: The queries dict maps "charged", "live", "dead", "checks". The
         fallback passes 3 values for a query with 2 placeholders.
  Impact: If called with uppercase status like "CHARGED", falls through to
          "checks" query → sqlite3.ProgrammingError: Incorrect number of
          bindings supplied.

Bug #13 — stripe_check() is a non-functional stub
  File: core/checker.py:223-224
  Code: return CheckResult("DEAD", "stripe_disabled", "Stripe", 0.0, ...)
  Issue: /st command calls stripe_check_cmd which uses this function. It
         always returns DEAD regardless of card validity.
  Impact: Users running /st always get "DEAD" result with no indication that
          Stripe is disabled. Misleading UX.

Bug #14 — Hourly quota consumed but never refunded on abandoned sessions
  File: handlers/mass_check.py:158-161, core/rate_limiter.py:89-103
  Issue: check_hourly_limit() reserves the full card count. If user ignores
         the price-range buttons, the conversation ends but hourly quota is
         permanently consumed. refund_hourly() is only called in cancel
         callback and cancel command, not on timeout/ignore.
  Impact: Users who start but don't complete a mass check lose hourly quota.

Bug #15 — SITE_ERROR_TRIGGERS are overly broad, causing false classifications
  File: core/checker.py:37-66, 98-101
  Issue: SITE_ERROR_TRIGGERS includes bare substrings like "timeout", "502",
         "503", "429", "cloudflare". Check uses simple substring matching.
         SITE_ERROR classification is checked FIRST (before CHARGED/LIVE).
  Impact: Legitimate decline like "error code 4293" matches "429". Response
          mentioning "cloudflare" triggers SITE_ERROR even if check succeeded.
          False positives override valid results.

Bug #16 — broadcast_cmd has no rate limiting between sends
  File: handlers/admin.py:307-317
  Issue: The loop sends messages to all users with no asyncio.sleep() between
         sends. Telegram bots are limited to ~30 messages per second.
  Impact: For 100+ users, Telegram returns RetryAfter/FloodWait errors. Most
          messages silently fail. Reported "sent" count is inaccurate.

Bug #17 — Database backup misses WAL and SHM files
  File: handlers/admin.py:440
  Code: shutil.copy2(db_path, str(backup_path))
  Issue: Database runs in WAL mode (set at database.py:149). In WAL mode,
         uncommitted data lives in .db-wal and .db-shm files. shutil.copy2
         only copies the main .db file.
  Impact: Backup may be missing recent writes. Restoring could lose data.
          Should use sqlite3.Connection.backup() or CHECKPOINT before copying.

Bug #18 — _pending_deletions dict grows unboundedly (memory leak)
  File: handlers/admin.py:454, 571
  Issue: _pending_deletions is a module-level dict. Entries added when owner
         runs /chk_all_site but removed only when buttons are clicked. If
         owner never clicks, entries stay forever.
  Impact: Memory leak. Each entry contains bad_stores list and metadata.

Bug #19 — New aiohttp ClientSession created per card check
  File: core/checker.py:157
  Code: async with aiohttp.ClientSession() as session:
  Issue: In mass check, shopify_check() is called per card. Each call creates
         a new ClientSession (TCP connection pool, cookie jar) and tears it
         down after one request.
  Impact: For 1000+ cards, creates/destroys 1000+ connection pools. Each needs
          a new TCP handshake + TLS negotiation. Adds ~200-500ms per card.

Bug #20 — Rate limiter _cleanup only runs on hourly limit checks
  File: core/rate_limiter.py:57-67
  Issue: _cleanup() is only called from check_hourly_limit() and
         refund_hourly(). The _cmd_last and _card_seen dicts are pruned inside
         _cleanup, but if a user only uses /sh, these dicts accumulate forever.
  Impact: Slow memory leak over days of operation.
